# Varwof Capability Specification (v2.0 — register)

This document defines the unified Capability encoding specification for the Varwof suite (pki-core / gateway / AIC / PA),
as well as the single source of truth for capability specifications (the register module) and the generation chain for derived artifacts (authz.json / permission documentation).
All modules' permission decisions, capability declarations, and authorization intersections must follow this document; assembling formats independently is prohibited.

## 1. Single Source of Truth for Capability Specifications: register

The **authoritative source** for capability specifications is the JSON scheme files embedded in the register module
(`register/varwof/*/v*.json`, e.g. `varwof/core/v1.json`, `varwof/gateway/v1.json`),
which can be overridden by disk directories (`vendor/product/v*.json`, directories injected as runtime configuration).

```
capability.json (authoritative schema)
      │ gen-authz  ──→ authz.json (roles/OU/namespaces/parameter defaults)
      │ gen-docs   ──→ *-capabilities.md (AI/human-readable permission documentation)
      │ gen-capability ──→ AI generates minimal-privilege capability per task (validated)
      ▼
Runtime: core issuance (capregistry validation) + authentication (authz.json policy)
        + gateway data plane (capregistry validation, opt-in) + SIGHUP hot reload
```

## 2. Structure

`Capability` has three fields (consistent across pki-types / core ca structures):

| Field | Type | Required | Description |
|---|---|---|---|
| `scheme_id` | string | Yes | Capability scheme namespace (see §3) |
| `capability_id` | string | Yes | Capability identifier, `domain:action` two-level (see §4) |
| `parameters` | []byte | No | Structured JSON object (see §5) |

Full permission identifier = `scheme_id:capability_id` (e.g. `varwof/core:cert:issue`),
uniformly generated by `Capability.FullID()`. All matching/intersection/authorization decisions must be based on the full identifier.

## 3. SchemeId Namespace (vendor/product)

| SchemeId | Domain | Description |
|---|---|---|
| `varwof/core` | PKI core management permissions | Corresponds to all core permissions in authz.json (ca/cert/user/...), 37 capabilities + 10 roles |
| `varwof/gateway` | Gateway management permissions | Gateway management API RBAC (listener/route/policy/...), 21 capabilities + 5 roles |
| `oracle/mysql` | Business data plane | Business product capabilities |
| `x-vendor/acme` | Third-party / standard protocols | External product capabilities |

> scheme_id is uniformly in `vendor/product` form (without version; version is in the scheme file's `version` field).
> Using bare `core`, `varwof-core-v1`, `mysql`, `test` or other non-standard schemes is not allowed.
> Business product schemes are defined and registered by the product itself (e.g. `oracle/mysql`).

## 4. CapabilityId Syntax (domain:action)

```
capability_id := domain ":" action
```

- `domain`: Capability domain. Core includes `ca`/`cert`/`crl`/`user`/`log`/`report`/`config`/`ra`/`cross-cert`/`webhook`/`key`/`dns`/`trust`/`agent`/`swagger`/`web`; gateway includes `listener`/`route`/`policy`/`plugin`/`agent`/`stats`, etc.
- `action`: Action (`create`/`delete`/`list`/`info`/`issue`/`revoke`/`renew`/`export`/`batch`/`generate`/`manage`/`read`/`write`/`approve`/`reject`/`import`/`recover`/`view`, etc.)

Examples:
- `varwof/core:ca:list` — List CAs
- `varwof/core:cert:issue` — Issue certificates
- `varwof/core:user:manage` — Manage users
- `varwof/gateway:route:update` — Update gateway routes
- `oracle/mysql:query:SELECT` — MySQL data plane query

### Matching Rules

- Exact match: `capability_id` matches exactly
- Wildcard: inherits `MatchCapability` semantics (`*`, `?`, `a:b:*` prefix), see §7 wildcard rules
- **Fast decision**: 90% of authorization scenarios only need `scheme_id:domain:action` three-level exact/wildcard matching,
  no need to parse `parameters`
- **Precise control**: when boundaries/ranges are needed, refer to `parameters` (§5)

## 5. Parameters (Structured JSON)

`parameters` stores the specific parameterized constraints of a capability and must be a valid JSON object.

| Common Parameter | Type | Description |
|---|---|---|
| `ca_scope` | string[] | Whitelist of CA names that can be operated on (sub-CA scope of effect) |
| `max_validity` | string | Maximum certificate validity period (Go duration, e.g. `"8760h"`) |
| `max_rows` | int | Maximum query row count (report/database capabilities) |
| `max_concurrent` | int | Maximum concurrent connections |

Example (limiting sub-CA scope):
```json
{
  "scheme_id": "varwof/core",
  "capability_id": "ca:issue",
  "parameters": {
    "ca_scope": ["Issuing CA", "Agent CA"],
    "max_validity": "8760h"
  }
}
```

> `parameters` semantics are defined by the scheme. Cross-scheme value inference is not performed (CA only does capability-level subset validation,
> parameter-level validation is only performed on grants with matching schemes).
> Parameter defaults are written by gen-authz into authz.json's top-level `capability_parameters`
> (key = `scheme:cap_id`), for runtime `HasParamDefault` queries.

## 6. Authorization Decision Flow

```
Request permission P (full identifier varwof/core:cert:issue)
  │
  ├─ 1. Fast decision: P ∈ authorized set (AIC capabilities / PA grants / role grants)
  │      └─ MatchCapability(P, grant.FullID()) → if matched, allow
  │
  ├─ 2. Precise decision: when grant has parameters
  │      └─ Validate request context (CA scope / validity / rows) vs parameters
  │
  └─ 3. Fail-closed: any check fails → reject
```

## 7. Wildcard Rules

- `*` matches any character sequence (can span `:`)
- `?` matches a single character
- `a:b:*` prefix match: matches all capabilities starting with `a:b:`
- Role grants commonly use prefixes: `ca:*`, `cert:*`, `gateway:*` (cross-scheme namespace wildcards)
- `*` (single character) matches all capabilities

## 8. Consistency Requirements

- All modules use `Capability.FullID()` (pki-types) for concatenation; duplicate implementations are prohibited
- `GrantIds()` (PA) returns a list of full identifiers
- AIC intersection (P∩C) is based on full identifier matching
- After authentication, `AuthUser.Permissions` must use full identifiers
- authz.json grants do not include the scheme prefix (e.g. `ca:list`), resolved at runtime based on the current scheme context;
  cross-scheme wildcards (e.g. the agent role's `gateway:*`) are handled by namespace
- Both the issuance side (pki-core) and gateway data plane perform capability registration validation: unregistered scheme/capability declarations = rejection
- Capability scheme changes must follow the register specification (modify `v*.json` → regenerate authz.json / permission documentation →
  SIGHUP hot reload); directly editing derived artifacts is prohibited to avoid drift from the authoritative schema

## 9. Toolchain Entry Points

- `register/cmd/gen-authz` — generates authz.json from scheme files (includes `.p7s` signature verification)
- `register/cmd/gen-docs` — generates AI/human-readable `*-capabilities.md` permission documentation
- `register/cmd/gen-capability` — validates AI-generated minimal-privilege capabilities (valid/redundant/over-privilege detection)
- For the complete workflow, see `register/README.md` and `register/AI_PROMPT.md`
